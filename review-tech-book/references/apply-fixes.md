# 审阅后修复模式

> 仅在用户明确要求“修复/优化/应用改进”时使用。审阅默认仍只报告。

## 触发与边界

- 触发词：`优化所有问题`、`修复这些问题`、`apply fixes`、`按报告修复`。
- 输入优先级：最新 `completed` review `report.md` → `findings/phase2.md` → 源 HTML。
- 不重开完整审阅；只实现报告中的修复批次。若发现新风险，记录到 `fix-report.md`，不要扩张范围。
- 翻译/整合/codebase 问题可以在用户明确要求时修复，但必须按类别批量处理，避免逐点微修补。

## 执行顺序

1. **P0 技术错误**：版本标注、API 说明、不可运行代码、断链、编号错误。
2. **P1 学习路径与结构**：章节拆分/合并、标题去重、交叉引用、导航更新。
3. **P2 风格与系统性残留**：翻译腔、术语残留、补充章节标识、格式一致性。
4. **P3 参考体验**：练习、自测、速查表、索引、实践项目。

每批完成后运行自动验证；失败时先修复失败项再进入下一批。

## HTML 修改守则

- 新增 HTML 文件时，同步更新所有带 sidebar 的页面导航，并验证 0 断链。
- 移动章节内容时，检查 `<main>`、`<article>`、`</main>`、`</article>` 数量匹配。
- 移出代码清单时，重新编号原章节清单；新章节可保留原编号或改为独立编号，但同一文件内必须连续。
- 拆章时更新目录、侧栏、前后文交叉引用、章节学习目标和章末要点。
- 添加 CSS 类时同时检查浅色/深色主题可读性。

## 修复报告

写入当前 review run 的 `fix-report.md`：

```markdown
# 修复报告

## 修复批次
| 批次 | 已修复 | 文件 | 验证 |
|------|--------|------|------|

## 验证结果
- validate_code.sh:
- 代码实机验证:
- 残余风险:
```

## 完成关卡

- [ ] 每个报告问题有对应修复或明确保留理由。
- [ ] 新增/移动页面已加入导航且无断链。
- [ ] HTML 结构检查通过。
- [ ] 翻译腔和术语扫描通过。
- [ ] 代码清单编号连续。
- [ ] 至少一个新增/改动代码示例做 V1 实机验证。
