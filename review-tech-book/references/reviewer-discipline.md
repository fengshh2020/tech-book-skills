# 审阅纪律协议

> 供 review-tech-book skill 使用。定义审阅过程中必须遵循的结构性纪律要求。

## ⚠️ 最高优先级规则（在读任何其他内容前记住这三条）

1. **每条发现必须有原文摘引**：没有原文摘引的发现 = 无效，不得写入报告。原文摘引必须是从源文件实际读取并复制的文本，不是改写或凭记忆描述。
2. **严重问题必须有证据**：🔴 标记至少 V2（读取了源文件对应行），🟠 标记至少 V2。API 移除时间线断言必须 V1 或 V3。V4 推断不得标记为严重。
3. **默认只报告不修复**：翻译/整合/代码库书籍问题回溯原 skill。只有用户明确要求才修改文件。

违反以上任何一条的报告视为不合格，需要修正后重新提交。

## 一、发现格式模板

每一条技术性发现（错误、问题、亮点）必须使用以下结构化格式。不允许纯段落式描述。

```
### [编号]. [章节] [简要标题] [严重程度标记]

- **位置**：`ChX 行NNN-NNN`（必须精确到行号范围）
- **原文摘引**：从源文件实际读取并复制的原文片段（≥1 行，含行号）
- **问题/评价**：基于原文的具体分析，说明为什么有问题或做得好
- **验证等级**：[V1]/[V2]/[V3]/[V4]（见第二节）
- **影响范围**：对读者的影响评估
- **建议修复**：具体的修复方法或改进方向（可选，严重错误必须提供）
```

**为什么强制此格式**：格式中的"原文摘引"字段要求审阅者必须实际打开并读取源文件。如果审阅者无法提供原文摘引，说明没有真正读过源文件，该发现的可靠性存疑。

**反例（不合格）**：
> Ch4 的学习目标包含了变量与可变性、函数与 lambda、类与对象等内容，但章节实际讲的是项目结构。

这个描述没有原文摘引，无法验证"包含"的内容是否真的存在。实际项目中恰好发生了一模一样的问题——声称学习目标包含 X/Y/Z，但源文件中根本没有。

**正例（合格）**：
> ### 4. Ch4（行 23-27）学习目标与内容错配 🔴
>
> - **位置**：`07_chapter4.html 行23-27`
> - **原文摘引**：
>   ```
>   <li>使用 if/elif/else 和 match/case 进行条件判断</li>
>   <li>掌握 for/while 循环和 break/continue 控制</li>
>   <li>理解异常处理的基本模式（try/except/finally）</li>
>   ```
> - **问题**：学习目标描述控制流语法，但章节标题是"项目结构与导入"，正文讲的是模块导入、包组织、虚拟环境。
> - **验证等级**：[V2] 已读取源文件行23-27确认原文内容
> - **影响范围**：读者从目录页就会产生错误预期
> - **建议修复**：将学习目标改为"理解语句与表达式的区别、使用 import 导入模块、理解 `__main__` 入口和虚拟环境"

## 二、验证等级体系

验证等级定义和强制规则见 `../../shared/verification-levels.md`。审阅场景的额外要求：

- 🔴 严重错误标记的问题，必须至少有 V2 验证等级（不能仅凭 V4 推断就标记为严重）
- 🟠 错误标记的问题，必须至少有 V2 验证等级
- 涉及 API 存在性、移除时间线的断言，必须达到 V1 或 V3
- V4 等级的发现应在报告中注明"未经验证，需二次确认"，严重程度自动降一级

**为什么需要等级**：实际项目中，审阅者声称 `link_to()` 在 Python 3.10 被移除（V4 推断，且推断错误），如果强制标注等级，读者会知道这条未经实机验证，可以降低信任度。

## 三、LLM 审阅者反模式

以下是从实际审阅错误中提炼的 LLM 审阅者高频失败模式。审阅过程中必须主动自检是否正在犯这些错误：

### 反模式 1：内容填充

**表现**：声称源文件中包含实际不存在的内容。典型场景："学习目标包含变量与可变性、函数与 lambda、类与对象"，但实际只有三条控制流目标。

**根因**：从对同类书籍的一般印象中填充内容，而非从源文件中读取。

**防护**：每条"源文件包含 X"的断言，必须在发现格式中提供原文摘引。如果无法提供原文，不要做出该断言。

### 反模式 2：虚假修正

**表现**：在纠正书籍错误的同时引入新的错误。典型场景：书籍说 `link_to()` "已弃用"（准确），审阅者"纠正"为"3.10 移除"（错误——实际是 3.10 弃用、3.12 移除）。

**根因**：凭记忆做出版本时间线断言而不验证。

**防护**：对 API 移除/弃用时间线的断言，必须达到 V1 或 V3 验证等级。不凭记忆声称"在版本 X 移除"。

### 反模式 3：来源混淆

**表现**：将原文本翻译误认为译者注，或反之。典型场景：原文"赋值表达式仍处于初期阶段"是英文原文的翻译，但被标记为"译者注"。

**根因**：不区分文本来源——原文本、译者注、审阅者评论三者性质不同，修复方式完全不同。

**防护**：翻译书籍中，每条问题必须标注来源：[原文]/[译者注]/[审阅者评论]。不标注来源的问题无法确定正确的修复方式。

### 反模式 4：范围膨胀

**表现**：将小问题描述为大问题。典型场景：学习目标实际只有 3 条错配，但被描述为 7 条；REPL 版本号差异被定性为"矛盾"而非"不一致"。

**根因**：审阅者倾向于让发现看起来更严重以显示审阅深度。

**防护**：使用结构化发现格式中的"原文摘引"字段限定范围。只描述能被原文证据支持的范围，不过度泛化。

### 反模式 5：跳过验证

**表现**：对可机械验证的事实不做实际验证。典型场景：声称 t-string API 错误但不运行代码，声称某函数已移除但不调用 `hasattr()`。

**根因**：验证需要额外的工具调用步骤，审阅者倾向于跳过。

**防护**：阶段 2 的选章策略中，至少选择 2 个章节的代码示例执行实际运行验证。对涉及 API 存在性/移除的断言，必须提供 V1 验证证据（如 `hasattr()` 调用结果）。

### 反模式 6：微修补循环

**表现**：每轮审阅只修复 1-3 处小问题就报告，导致 80+ 轮审阅仍在修错字和排版。典型场景：Round 35 修 3 处错字 → Round 36 修 3 处病句 → Round 37 修 1 处切片说明 → ...无止境。

**根因**：审阅者倾向于"找到一个问题就修一个"，而不是先做全书扫描再批量处理同类问题。

**防护**：每轮审阅前先做全书扫描，收集同类问题完整清单，按类别形成批量修复计划。若用户明确要求进入 apply-fixes 模式，单轮修复量应至少覆盖一个完整问题类别（如"全书错字"、"全书排版"、"全书翻译腔"），而不是 1-3 个散点。参见 SKILL.md 审阅纪律第 1 条。

### 反模式 7：越权修复

**表现**：审阅者直接修复翻译质量或整合质量问题，而非报告后交回原 skill 处理。典型场景：审阅轮次中修改翻译腔措辞，但因不了解原始翻译上下文而引入新问题。

**根因**：审阅者有修复能力就直接修复，不区分问题归属。

**防护**：区分问题归属（翻译质量 / 整合质量 / 书籍本体问题）。默认只报告不修复；只有用户明确要求 apply-fixes 时才修改文件。翻译和整合问题应回溯原 skill 处理。参见 SKILL.md 审阅纪律第 2 条。

## 四、阶段关卡检查

每个阶段完成、写入报告前，执行以下关卡检查。检查不通过则返回修正后再写入：

### 通用关卡（每个阶段）

- [ ] 本阶段所有发现是否有原文摘引？
- [ ] 本阶段是否包含 V4 推断且未标注"未经验证"？
- [ ] 🔴/🟠 标记的问题是否至少有 V2 验证等级？
- [ ] 是否犯了第三节的任何反模式？（逐条自检）

### 阶段 2 特殊关卡

- [ ] 至少 2 个章节的代码示例是否做了实际运行或逐行审查？
- [ ] 所有"API 已移除/弃用"的断言是否有 V1 或 V3 证据？
- [ ] 如果是翻译书籍，是否区分了 [原文] 和 [译者注]？
- [ ] 版本时间线断言（"X 在版本 Y 引入/移除"）是否查阅了权威来源？

### 阶段 4 特殊关卡

- [ ] P0 建议是否都有对应的阶段 2 发现支撑？（不能在 P0 中提出阶段 2 未发现的问题）
- [ ] 改进建议的具体位置是否与阶段 2 的发现位置一致？
- [ ] 一句话总结是否指向了实际发现的最关键问题（而非泛泛而谈）？

## 五、增强自审清单

报告完成后、交付前，执行以下自审。自审结果作为报告附录的一部分写入。

### A. 事实性断言审计

扫描报告中所有涉及以下类型的断言，逐条检查：

| 断言类型 | 检查方法 | 合格标准 |
|----------|----------|----------|
| "API X 已移除" | 运行 `hasattr()` 或查 docs | 有 V1 或 V3 证据 |
| "代码不可运行" | 提取并执行代码 | 有 V1 证据 |
| "从版本 Y 引入" | 查 What's New / PEP | 有 V3 证据 |
| "学习目标包含 X" | 读取源文件对应行 | 有 V2 证据 + 原文摘引 |
| "译者注说 X" | 读取源文件确认是译者注 | 标注了 [译者注] 来源 |

对不通过的断言：降低严重程度 + 标注"⚠ 自审：未充分验证"。

### B. 反模式复核

逐条回顾第三节的 7 个反模式，确认没有在报告中犯其中任何一个。如果发现了，修正对应条目。

### C. 严重程度校准

重新审视每个 🔴 标记的问题：如果读者按这个描述去修复，是否真的能解决一个"代码无法运行或严重误导"的问题？如果不确定，降级为 🟠。

### D. 范围校准

重新审视每个"包含 X/Y/Z"式的描述：是否每个 X/Y/Z 都能在源文件中找到原文？去除不能被原文证据支持的部分。
