# 查询分解与迭代策略

research 「拆」「查」两步的深度参考。按需读，不常驻。

## 查询分解

### 分解原则

1. **一个子查询回答一个维度**——"GO2 SDK 支持哪些运动模式"和"GO2 SDK 的通信协议是什么"是两个子查询。
2. **子查询可独立验证**——答案可独立确认对错。
3. **子查询间有依赖时标注**——"B 的答案依赖 A 的结论"。

### 分解模板

```
原问题：{用户问题}

子查询 1：{要回答什么}
  优先源：{官方文档 / SDK 源码 / …}
  验证方式：{官方文档确认 / 源码确认 / 实测}

子查询 2：{要回答什么}
  优先源：{…}
  依赖：子查询 1（如果 1 的答案是 X，则查…）
```

### 定向调研请求（被 tech-proposal 等调用时）

调用方提供结构化请求，直接用，不重新分解：

```
调研请求：
- 目标：{一句话}
- 需确认领域：[{…}, {…}]
- 验证要求：硬约束须官方文档/源码确认，不接受推断
- 产出格式：Finding Block
```

## 来源质量判断

| 优先级 | 来源类型 | 信任度 | 何时用 |
|--------|----------|--------|--------|
| 1 | 官方文档 / spec / PEP / RFC | 最高 | API 行为、语言特性、协议细节 |
| 2 | 源码（GitHub / 本地） | 高 | 实际行为、边界条件、实现细节 |
| 3 | 一方 API 文档 | 高 | SDK 接口、配置选项 |
| 4 | 权威博客 / 技术委员会 | 中 | 最佳实践、迁移指南 |
| 5 | Stack Overflow / 社区 | 低 | 仅作线索，不作证据 |

**不接受的来源**：AI 生成的博客（无人类审核痕迹）、未署名转载、无原始引用的二手总结、未标注适用版本的过时文档。

**交叉验证**：🔴 严重论断 ≥2 个独立来源；🟠 重要论断 ≥1 个高信任来源；推断必须标注并写明依据。

## 迭代策略

**何时再来一轮**：Gaps 非空且知道该查什么（有明确追加方向 / 已有来源暗示另一来源存在 / 子查询依赖解锁新路径）。

**何时停**：答案覆盖所有子查询 → 正常结束；Gaps 无法通过搜索填补（需实机 / 需人类决策 / 源不存在）→ 诚实记录；3 轮耗尽 → 交付部分答案。

**每轮加深而非拓宽，不重复搜同一源**：第 1 轮广度覆盖所有子查询；第 2 轮针对 Gaps 换源类型追踪（查了文档没找到 → 查源码）；第 3 轮换角度 / 换关键词作最后尝试。

## 工具与源不可达兜底（runtime-neutral）

不同 runtime 可用工具不同（有的有 WebSearch/Context7/codegraph，有的只有 curl/grep）；工具缺位或搜索连续返空时：

- **已知权威 URL 直取**（首选）：从 changelog / 索引页定位具体页 URL，用 runtime 任意 fetch（`curl` / `WebFetch` / `WebReader`）直拉（如 `https://peps.python.org/pep-0695/`）——比通用搜索更准、更稳。
- **源码**：`gh search code` / `grep.app` / clone 后 `grep -rn`；本地用 Glob/Grep。
- **搜索连续返空**：换关键词 / 加 `site:` / 换源类型（文档 ↔ 源码 ↔ 社区）/ 直取已知权威 URL，而非反复跑同一查询。
- **runtime 无任何 fetch 工具**：诚实标 Gaps（"无法在线验证"）、降置信度，**绝不靠猜填答案**。
