# 知识扩展方法论

> 供 codebase-book 阶段 3 和阶段 4 使用。定义如何从代码延伸到设计原理、工程实践和生态知识。

---

## 核心原则

知识扩展服务于一个目标：**让读者不仅理解代码做了什么，还理解为什么这样做，以及背后的通用知识**。扩展的边界是读者理解本项目代码所需的知识——不发散到读者暂时不需要的领域。

判断标准：如果读者不了解某个知识点，就无法真正理解某段代码的设计意图或实现原理，那么这个知识点就应该扩展讲解。

反向判断：如果知识点只是“顺便相关”、不会影响读者理解当前代码，就不要扩展。代码库书籍不是百科全书。

---

## 知识扩展分类

### 类型 1：语言特性

**触发条件**：代码使用了语言的特定特性（如 Python 的描述符协议、Rust 的生命周期、Go 的 goroutine）。

**扩展方式**：
1. 解释该特性的核心机制（不是完整教程，而是本项目用到的部分）
2. 说明代码为什么需要这个特性（解决了什么问题）
3. 提供一个简化的独立示例，展示该特性的基本用法

**示例**：代码使用了 `__slots__` → 扩展讲解 Python 实例属性存储机制、`__dict__` 与 `__slots__` 的内存差异、为什么本项目选择使用 `__slots__`。

### 类型 2：框架/库原理

**触发条件**：代码依赖了特定框架或库的核心机制（如 React 的 Fiber 调度、Django 的 ORM 查询构建、Express 的中间件栈）。

**扩展方式**：
1. 解释框架该机制的核心工作原理
2. 说明本项目的使用方式与框架推荐方式是否一致
3. 如果有常见的误解或陷阱，指出

**示例**：代码使用了 SQLAlchemy 的 session → 扩展讲解 session 的生命周期管理、工作单元模式、延迟加载策略，以及本项目如何管理 session 的创建和关闭。

### 类型 3：设计模式

**触发条件**：代码中明显应用了某个设计模式（如策略模式、观察者模式、装饰器模式）。

**扩展方式**：
1. 解释该模式的意图和核心结构
2. 展示本项目中的具体实现如何对应到模式
3. 对比替代方案：如果不使用这个模式会怎样

**示例**：代码使用中间件链处理请求 → 扩展讲解责任链模式/中间件模式的通用结构、在本项目中的变体、与直接 if-else 分支的对比。

### 类型 4：算法和数据结构

**触发条件**：代码实现了特定算法或选择了特定数据结构，且这个选择影响系统的行为或性能。

**扩展方式**：
1. 解释算法/数据结构的核心思想和复杂度特征
2. 说明在本项目场景下为什么它是合适的选择
3. 如果有经典替代方案，简要对比

**示例**：代码使用 LRU 缓存 → 扩展讲解 LRU 的实现原理（双向链表 + 哈希表）、O(1) 操作保证、在本项目的缓存淘汰场景中的适用性。

### 类型 5：工程实践

**触发条件**：代码体现了特定的工程实践（如错误处理策略、日志规范、配置管理、测试方法）。

**扩展方式**：
1. 解释该实践解决的问题和行业共识
2. 说明本项目的具体做法
3. 对比常见的替代做法和各自的权衡

**示例**：代码使用结构化日志 → 扩展讲解结构化日志 vs 非结构化日志、在日志聚合系统中的优势、本项目的日志规范。

## 知识扩展的写作规范

### 内容组件

知识扩展在 HTML 中使用 `sidebar` 组件：

```html
<div class="sidebar">
  <p class="sidebar-title">深入理解：[知识点名称]</p>
  <p>扩展内容...</p>
</div>
```

工程实践要点使用 `warning` 变体：

```html
<div class="sidebar warning">
  <p class="sidebar-title">工程实践：[实践名称]</p>
  <p>实践内容...</p>
</div>
```

### 深度控制

每个知识扩展点控制在 3-8 段以内。遵循以下深度原则：

- **一句话能说清的** → 行内解释，不使用 sidebar
- **一段话能说清的** → 正文中的简要说明
- **需要 3-8 段说清的** → sidebar 知识扩展框
- **需要更长篇幅的** → 考虑是否需要独立章节，而非无限扩展 sidebar

### 密度控制

知识扩展的数量必须服务阅读节奏：

- 每章优先选 3-6 个真正关键的扩展点
- 同一小节内最多 1 个 sidebar；多个相关知识点合并成一个“背景知识”块
- 连续两个代码块之间不要再插入多个知识框
- 已在前文解释过的概念，后续只引用，不重复展开
- 概念解释结束后必须回到项目代码，说明它如何帮助理解当前实现

### 准确性要求

- 扩展内容中的事实性断言必须标注验证等级
- 语言特性的行为描述至少需要 V3（文档对照）或 V1（实机验证）
- 不确定的内容标注 `[待确认]`，不在书中传播未验证的推断
- 引用具体的官方文档、RFC、规范编号（如 PEP 484、RFC 7231）
- 最终 HTML 中不要保留 `[待确认]`；若无法验证，降级为报告中的已知限制

## 知识扩展清单生成

阶段 3 设计章节时，对每个模块从 `.book-doc/analysis/{module}.md` 的「隐含知识」字段提取扩展点，归类到上述 5 种类型，确定扩展深度，写入 chapter-plan.md 的每章内容计划中。

扩展清单格式：

```markdown
### 知识扩展项

| 知识点 | 类型 | 触发位置（文件:行） | 扩展深度 | 前置知识 |
|--------|------|---------------------|----------|----------|
| Python 描述符协议 | 语言特性 | models.py:45 | sidebar | 面向对象基础 |
| 工作单元模式 | 设计模式 | db/session.py:23 | sidebar | 数据库事务基础 |
```
