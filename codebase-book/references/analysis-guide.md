# 代码库分析方法论

> 供 codebase-book 阶段 2 使用。定义如何系统化地深入分析代码库的每行代码和设计决策。

---

## 分层分析策略

代码库理解分三层递进：

### 第一层：结构理解

**目标**：建立模块间关系图，不读实现细节。

- 读取每个文件的导出列表（public API）：函数签名、类接口、类型定义、常量
- 建立模块依赖图：谁 import 了谁、调用链走向
- 识别分层架构：表现层 → 业务层 → 数据层，或类似划分
- 标记模块角色：入口、核心、适配器、工具、配置

**产出**：模块关系图 + 每个模块的角色和公开接口概览。

**纪律**：这一层只建立地图，不急着写解释。不要把目录树直接变成章节目录；章节顺序由读者学习路径决定。

### 第二层：逻辑理解

**目标**：理解每个模块内部的实现逻辑。

按分析顺序（入口 → 核心 → 基础设施 → 工具）逐文件分析：

1. **读取完整文件**，不跳过任何行
2. **标注关键段落**：
   - 初始化/配置逻辑
   - 核心算法或业务规则
   - 数据转换和处理
   - 错误处理和边界条件
   - 并发/异步逻辑
   - 资源管理（连接、文件、内存）
3. **追踪数据流**：数据从哪来、怎么变换、到哪去
4. **追踪控制流**：请求/事件触发的完整执行路径
5. **记录源码证据**：关键解释必须带文件路径和行号范围，例如 `src/server.py:42-88`

不要逐行复述语法。分析目标是找出行为、边界、状态变化、错误路径和依赖关系。

### 第三层：决策理解

**目标**：推断并记录每个设计决策的"为什么"。

从代码证据推断设计意图：

| 代码证据 | 可推断的决策 |
|----------|------------|
| 选择了特定的数据结构（如 HashMap 而非 BTreeMap） | 性能权衡（O(1) vs O(log n) 查找） |
| 使用了特定的设计模式（如策略模式而非 if-else） | 可扩展性优先 |
| 错误处理策略（异常 vs Result vs panic） | 健壮性/简洁性权衡 |
| 抽象层级（接口/泛型/具体类型） | 灵活性 vs 简洁性 |
| 命名约定和代码组织方式 | 团队/社区惯例 |
| 依赖选择（用库 A 而非库 B） | 功能/性能/许可证/维护状态考量 |
| 测试覆盖模式（单元/集成/e2e 比例） | 质量策略 |

## 分析文件格式

每个模块的分析文件 `.book-doc/analysis/{module}.md` 包含以下结构：

```markdown
# 模块名

## 概览
- 路径：`src/module/`
- 角色：[核心/工具/基础设施/...]
- 依赖：[被依赖列表] → [依赖列表]

## 文件分析

### `filename.ext`

#### 接口契约
- 导出的函数/类/类型
- 参数语义和返回值
- 副作用和前置条件
- 源码证据：`path:line-line`

#### 实现逻辑
- 关键代码段 + 行为说明
- 数据流和控制流
- 错误路径和边界条件

#### 设计决策
- [决策描述] → 原因：[V等级] [证据]
- [决策描述] → 原因：[V4 推断] [推断依据]

#### 隐含知识
- 语言特性：[如 async/await, 泛型约束, 生命周期]
- 框架 API：[如 Express 中间件机制, Django signal]
- 设计模式：[如观察者, 工厂, 装饰器]
- 算法/协议：[如 Raft, 一致性哈希, LRU 缓存]

## 测试分析
- 测试覆盖的行为契约
- 边界条件测试
- 揭示的设计意图
```

## 决策识别清单

分析每个模块时，主动检查以下方面的设计决策：

### 架构层

- [ ] 模块划分方式和边界
- [ ] 依赖方向（是否存在循环依赖）
- [ ] 通信方式（直接调用/事件/消息队列/共享状态）
- [ ] 错误传播策略
- [ ] 配置管理方式（硬编码/配置文件/环境变量）

### 代码层

- [ ] 数据结构选择
- [ ] 算法选择
- [ ] 抽象层级
- [ ] 命名约定
- [ ] 代码组织方式（按功能/按特性/按层级）
- [ ] 并发模型（同步/异步/多线程/多进程）

### 工程层

- [ ] 测试策略和覆盖范围
- [ ] 依赖管理（版本锁定/最小依赖）
- [ ] 构建和发布流程
- [ ] 日志和监控策略
- [ ] 安全考量

## 大型代码库处理

当源文件超过 30 个且当前 agent runtime 支持独立 worker 时，采用分批并行分析：

1. 按模块分组，每组 5-8 个相关文件
2. 使用独立 worker/agent 并行分析各组；不支持并行时按组串行执行
3. 合并结果时验证组间依赖一致性

每组的分析产出是独立的 `.book-doc/analysis/{module}.md` 文件，合并阶段只检查跨组引用的一致性。

## 防止流水账

分析文件不是章节草稿。以下内容不要直接搬到书里：

- 每个函数一小节的机械目录
- 对 import、简单赋值、样板配置的逐行解释
- 没有设计含义的“这里调用了 X，然后调用了 Y”

应提炼为：

- 核心执行路径：一次请求/命令/事件如何穿过系统
- 关键抽象：哪些类型、接口、协议承担稳定边界
- 设计取舍：性能、可扩展性、可测试性、部署复杂度之间如何权衡
- 读者任务：读完后能运行、修改、扩展或调试什么
