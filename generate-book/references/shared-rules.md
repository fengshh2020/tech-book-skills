## 铁律 (IRON LAW)

**NO OUTPUT WITHOUT FRESH READ EVIDENCE. NO GATE SKIP. NO TITLE-ONLY INFERENCE. NO CONTENT SHRINKAGE.**

违反这条规则的字面意思，就是违反这条规则的精神。

## 预检清单 (Pre-Flight Check)

启动前必须验证以下条件。任何一项失败 = 停止并告知用户，不尝试"凑合"。

```bash
# 1. 确认 run_dir 可写
mkdir -p <run_dir> && touch <run_dir>/.preflight && rm <run_dir>/.preflight

# 2. 确认 output 目录可创建
mkdir -p <run_dir>/output

# 3. 确认 workflow.py 存在（Gate 检查依赖它）
test -f scripts/workflow.py || echo "WARNING: workflow.py not found, Gate checks will use manual verification"

# 4. 确认 assets 存在
test -f assets/style.css && test -f assets/script.js || echo "WARNING: CSS/JS assets missing, HTML assembly will skip styling"
```

**模式特定预检**：
- **单源**：确认源文件（EPUB/HTML）可读取
- **多源**：确认每个源文件可读取，数量 >= 2
- **代码库**：确认代码库路径存在且包含源文件；确认有基本构建/运行命令

**预检失败处理**：
- 文件不可读 → 告知用户具体路径，请求修复
- 脚本缺失 → 记录警告，改用手动验证（见下方降级方案）
- 目录不可写 → 告知用户权限问题

## 标准关卡自检清单

Gate 编号是模式特定的（例如 Gate 3 在单源/多源模式中 = 验证，在代码库模式中 = 生成）。始终参考当前模式的流程文件确定 Gate 含义。

每个关卡运行前，确认以下均不为真：
- 任何参考文件在本阶段未被重新阅读
- 任何"我已阅读"的声明缺少结构证据
- 任何章节的输出大小 < 源文件的 80%
- Gate 检查未实际运行（仅口头声称）

如有任何一项为真：先修复再运行关卡。

## 反偷工减料规则

遵循 `shared/anti-slacking.md`。核心要点：
- 每个阶段开始时重新阅读参考文件，附带结构证据（段落数、代码块数、具体术语）
- 不跳过子阶段，不凭标题推断，Gate 没有"大概"
- 单源模式额外要求：验证 1:1 段落映射
- 代码库模式额外要求：每个论断需要 file:line 证据

### 输出文件验证

每个阶段的输出必须通过文件级验证，防止静默失败：

| 检查项 | 通过标准 | 失败处理 |
|--------|----------|----------|
| 文件存在 | 输出文件路径存在 | 重新执行该子阶段 |
| 文件非空 | 文件大小 > 0 | 重新执行该子阶段 |
| 大小合理 | >= 预期大小的 50%（防止截断） | 扩展内容 |
| 无占位符 | 不含 `[待确认]`、`TBD`、`TODO` | 补充内容 |
| 编码正确 | UTF-8，无乱码 | 重新生成 |

**验证命令**（在每个子阶段输出后执行）：
```bash
# 检查文件存在且非空
test -s <output_file> || echo "FAIL: <output_file> missing or empty"

# 检查大小（示例：核心章节 >= 20KB）
wc -c <output_file> | awk '{if ($1 < 20480) print "FAIL: too small ("$1" bytes)"}'

# 检查无占位符
grep -l '\[待确认\]\|TBD\|TODO' <output_file> && echo "FAIL: contains placeholders"
```

### 模式检测与歧义处理

输入可能不明确。按以下规则处理歧义：

| 情况 | 判断规则 | 处理 |
|------|----------|------|
| 输入是目录路径 | 检查是否包含源代码文件（.py, .js, .go, .rs 等） | 是 → 代码库模式 |
| 输入是目录路径 | 检查是否包含书籍文件（.epub, .html） | 是 → 根据文件数量选择单源/多源 |
| 输入混合了书籍和代码 | — | 询问用户："检测到书籍文件和代码文件，请问主要目标是什么？" |
| 输入是单个文件 | 检查文件类型 | .epub/.html → 单源模式 |
| 输入是多个文件 | 数量 | 1 个 → 单源，2+ → 多源 |
| 不确定 | — | 询问用户确认模式 |

## 失败模式识别

### 通用失败模式

**1. 跳过重新阅读**
- 模型说："我之前已经加载了翻译规则" / "我记得整合计划"
- 真相：上下文被压缩过，规则已经模糊
- 检测：progress.md 中缺少本阶段的阅读确认
- 修复：重新阅读文件，记录确认及结构证据

**2. 只凭标题推断**
- 模型说："第 5 章讲函数，所以包括参数、返回类型、重载"
- 真相：第 5 章讲的是函数对象和 lambda
- 检测：证据使用了泛化术语
- 修复：打开文件，阅读完整内容，用具体术语记录证据

**3. 绕过 Gate**
- 模型说："Gate 通过了——所有检查看起来都不错"
- 真相：Gate 脚本从未实际运行
- 检测：progress.md 中没有粘贴脚本输出
- 修复：运行 Gate 命令，粘贴完整输出

**4. 内容缩减**
- 模型说："章节生成成功"
- 真相：源章节 40 段，输出只有 15 段
- 检测：输出文件 < 源章节大小的 80%
- 修复：扩展输出以匹配源深度

### 多源模式失败模式

**5. 补丁式整合**
- 模型说："所有源都已整合"
- 真相：一个源贡献了 80% 的标记，其他源只出现在 1-2 个章节
- 检测：Coverage Guardian 显示底线规则违规
- 修复：扩展代表性不足的源的贡献

### 代码库模式失败模式

**6. 仅凭名称分析**
- 模型说："函数 `processData` 处理数据"（只读名称，没读函数体）
- 真相：遗漏错误处理、副作用、算法复杂度
- 检测：分析中缺少 file:line 引用
- 修复：读函数体，用 file:line 记录实际行为

**7. 罗列而非讲解**
- 模型说："函数 A 做 X，函数 B 做 Y"
- 真相：孤立罗列，读者无法形成连贯理解
- 检测：章节缺乏叙事线索
- 修复：沿执行路径或设计线索展开，讲述连贯的故事

**8. 内容缩减（代码库）**
- 模型说："章节已生成"（核心章节只有 5KB）
- 真相：读者只看到表面概述
- 检测：核心章节 < 20KB，概览 < 10KB
- 修复：扩展浅层部分，补充代码和解释

## Coverage Guardian（覆盖守护者）

**适用范围**：仅多源模式。单源和代码库模式不使用。

**用途**：检测并防止覆盖缺口、偷工减料和表面化整合。

**规则**：
1. **底线规则**：任何源书籍的标记数不得少于总标记数的 10%
2. **单章最低要求**：被映射为"主要"或"次要"来源的章节必须有 >=3 个整合标记
3. **补丁式检测**：标记全部出现在 <=2 个章节中 = 补丁式整合
4. **输出大小守护**：章节输出 >= 整合的最大源章节大小的 80%

**命令**：
```bash
python scripts/workflow.py generate-book <run_dir> coverage_report
python scripts/workflow.py generate-book <run_dir> coverage_guard
```

**运行时机**：Phase 2 完成后、Phase 3 验证中、Phase 4 报告中。

## 质量标准

**通用**：
- 每项新增内容都有来源、位置、收益说明
- 重复内容已合并或交叉引用
- 输出可通过 `report.md` 进入 review-tech-book 流程
- 术语、编号、导航、图片、代码注释在首次通过时即正确

**单源模式**：自然的中文，无翻译腔；保持 1:1 段落映射。

**多源模式**：读者无法辨识内容来源；章节骨架通过反向覆盖检查；整合等级仅限 L3（重组）或 L4（完全融合）。

**代码库模式**：每个论断有 file:line 证据；核心章节 >= 20KB，概览 >= 10KB；代码:解释 >= 1:1；覆盖错误路径和设计决策的替代方案/权衡取舍。

## 子 Agent 编排

完整规则见 `references/agent-orchestration.md`。关键约束：

1. **最大并发数**：5 个 Agent
2. **单源 Phase 0**：顺序阅读，一个 Agent
3. **单源 Phase 1**：单个 Agent 翻译，逐章顺序
4. **单源 Phase 2**：组装 Agent，顺序执行
5. **多源 Phase 0**：每本书一个 Agent，最多 3 本并行
6. **多源 Phase 1**：单个 Agent（全局视角）
7. **多源 Phase 2**：一次一个章节，单章内最多 3 个 Agent 并行
8. **代码库 Phase 0**：单个 Agent 扫描代码库
9. **代码库 Phase 1**：每核心模块一个 Agent，最多 3 个并行
10. **代码库 Phase 2**：单个 Agent 制定计划（全局视角）
11. **代码库 Phase 3**：章节数 > 5 时可并行，每批 2-3 章
12. **验证**：最多 3 个 Agent 并行
13. **错误恢复**：重试一次；第二次失败 = 暂停并询问用户
