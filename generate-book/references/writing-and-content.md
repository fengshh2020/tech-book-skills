# 写作与内容指南

> 供 generate-book（代码库模式）阶段 3-4 使用。定义写作原则、内容深度标准和知识扩展方法。

## 写作原则

1. **叙事连贯**：代码讲解是讲故事，不是列清单。沿执行路径、数据流或设计思路用连贯叙事串联代码，读者读完后能在脑中重建完整的执行画面
2. **先图后文**：复杂流程、架构、状态变化先用图表展示全局，再用叙事深入细节。读者先建立视觉框架，再填充代码细节，认知负荷显著降低
3. **设计优先**：先讲"为什么这样设计"，再讲"代码如何实现"
4. **深度优先**：宁可少覆盖，也要讲透——有代码、有分析、有背景知识、有权衡
5. **不重复**：同一机制讲一次，后续交叉引用
6. **结构服务内容**：章节结构由内容逻辑决定，不套用固定模板
7. **就地讲透**：读者需要的背景知识在当前上下文讲到位，不要求外查

## 叙事驱动的代码讲解

### 核心方法：讲好一个故事

代码讲解的首要任务不是"覆盖每个函数"，而是**让读者理解一条完整的思路**。

**好的写法**——叙事驱动：

> 当一条导航请求到达时，`Navigator.plan()` 首先将目标坐标转换到栅格空间（`planner.py:L34-38`），这一步是必要的，因为后续所有路径计算都在离散栅格上进行，浮点坐标无法直接用于搜索。
>
> 转换完成后，调用 `PathPlanner.find_path()` 启动 A* 搜索。搜索的核心循环在 `planner.py:L67-98`，每次从优先队列中弹出 f_score 最小的节点，检查是否到达终点，否则展开邻居。这里的关键设计选择是使用 8 方向邻居而非 4 方向——代价是搜索空间更大，但路径质量明显更优，对角线移动能减少 15-20% 的路径长度。
>
> ```python
> # planner.py:L67-82
> while open_set:
>     current = heapq.heappop(open_set)
>     if current == goal:
>         return reconstruct_path(came_from, current)
>     for neighbor in get_neighbors(current, directions=8):
>         tentative_g = g_score[current] + movement_cost(current, neighbor)
>         ...
> ```
>
> 搜索成功后，`reconstruct_path()` 通过 `came_from` 字典反向追踪路径。返回的路径是栅格坐标序列，由 `Navigator` 在 `planner.py:L105-112` 转换回世界坐标并做平滑处理。

这段讲解的特点是：**读者跟着一条请求的完整流程走**，代码片段在叙事需要的时候自然出现，参数和设计决策在上下文中解释，不会被 sidebar 打断思路。

**坏的写法**——碎片拼贴：

> `Navigator.plan()`：导航规划函数。参数：`goal` (tuple)——目标坐标。返回值：路径列表。
>
> ```python
> def plan(self, goal):
>     grid_goal = self.to_grid(goal)
>     path = self.planner.find_path(self.start, grid_goal)
>     return self.to_world(path)
> ```
>
> 下面讲解 `PathPlanner.find_path()`...
>
> [sidebar: 深入理解 A* 算法...]
>
> `PathPlanner.find_path()`：A* 搜索函数。参数：`start` (tuple)...

这段的问题是：**读者看到的是孤立的函数签名列表**，每个函数只有一段代码和一个简短说明，中间被 sidebar 打断，无法理解这些函数如何协作完成一个完整任务。

### 叙事组织方式

根据内容类型选择合适的叙事主线：

| 主线类型 | 适用场景 | 组织方式 |
|----------|---------|----------|
| **执行路径** | 请求处理、数据流、管道 | 跟随一次真实执行从入口到出口 |
| **数据流** | 数据转换、ETL、状态机 | 跟随数据对象从创建到消费 |
| **设计主题** | 架构决策、模式应用 | 围绕一个设计问题展开，代码作为解决方案展示 |
| **算法深度** | 核心算法、数据结构 | 从问题到思路到实现到参数影响 |

### 代码片段在叙事中的角色

代码片段是叙事的**证据**，不是叙事的**主体**：

- **先讲思路，再贴代码**：读者先知道要做什么，再看代码怎么做
- **代码后紧跟分析**：不是贴完代码就跳到下一个函数，而是分析这段代码的关键设计、参数影响、边界情况
- **长代码只贴关键段**：> 80 行的函数只贴关键 20-30 行，标注在源文件中的位置
- **不在叙事中间插入 sidebar**：如果背景知识是理解当前代码的前提，直接在叙事中讲（作为背景段落），不要用 sidebar 打断流程

**按代码长度选展示方式**：

| 代码长度 | 展示方式 |
|---|---|
| < 30 行 | 完整展示 |
| 30–80 行 | 分段展示，标注在源文件中的位置 |
| > 80 行 | 只贴关键 20-30 行，其余用叙事说明 |

代码块标注文件路径 + 行范围：`文件：src/module/core.py 第 23-67 行`。

**参数和错误路径的讲解方式**

参数不在函数签名处机械罗列，而是在**代码执行到该参数时**自然讲解：

> ...搜索使用 `heuristic_weight`（默认 1.0）控制启发式权重。设为 1.0 保证最优路径；设为 > 1.0 会加速搜索但可能牺牲路径质量。在 `planner.py:L72` 的 f_score 计算中，这个参数直接影响搜索的探索方向。

错误路径同样在执行到对应代码时讲解，不单独成节：

> 如果起点在障碍物内（`planner.py:L45` 的栅格值检查），`find_path()` 会抛出 `InvalidStartError`。`Navigator` 在 `planner.py:L115` 捕获这个异常并返回空路径，同时记录警告日志。下游的 `Controller` 收到空路径后会进入待命状态。

## 可视化与认知负荷控制

### 核心原则：先图后文

人类大脑处理视觉信息的速度比文本快 6 万倍。在深入代码细节之前，先用图表给读者建立全局视觉框架，读者的认知负荷会显著降低。

**标准模式**：图表展示全局 → 叙事讲解细节 → 代码展示实现

### 图表类型与使用场景

**用 Mermaid 文本写图**（[ADR-0004](../../../docs/adr/0004-diagrams-mermaid-to-png.md)）。在 MD 中直接写 ` ```mermaid ` 围栏，下一行写图注（以"图"开头触发自动编号）。builder 构建期用 mermaid-cli 渲染为 `diagrams/*.png` 嵌入 MD 版与 HTML 版；渲染器不可用时降级（HTML 运行时渲染 / GitHub MD 原生渲染）。**证据（file:line）写在图注里。**

```mermaid
flowchart LR
  Client -->|POST| Service
```
图：请求链路（client.py:42）

Mermaid 图类型选择：`flowchart`（流程/架构）、`sequenceDiagram`（时序/调用链）、`stateDiagram-v2`（状态机）、`classDiagram`（类型关系）、`gitGraph`（演进）。下表"图表类型"对应到 Mermaid 类型即可。

| 图表类型 | 适用场景 | 认知收益 |
|----------|---------|----------|
| **流程图** (`kind: flow`) | 执行路径、请求处理、数据流 | 读者一眼看清全局流程，不用从代码片段中拼凑 |
| **时序图** (sequenceDiagram) | 模块间交互、回调链、事件流 | 看清谁调用谁、时序关系、异步边界 |
| **状态图** (stateDiagram) | 状态机、生命周期、连接管理 | 理解状态转换条件和约束 |
| **类图** (classDiagram) | 类关系、接口继承、组合 | 看清职责边界和协作关系 |
| **数据流图** (graph) | 数据变换管道、ETL | 看清数据从原始到最终的完整变换链 |

### 何时必须用图

以下场景**必须有图表**，不能只用文字描述：

- **3 个以上模块协作**：用流程图或时序图展示模块间关系
- **状态转换**：用状态图展示状态机
- **复杂执行路径**：在进入代码走查前，先用流程图展示全局路径
- **数据变换链**：用数据流图展示数据从输入到输出的变换过程
- **设计决策对比**：用表格对比替代方案的优劣

### 何时用表格

表格是降低认知负荷的最有效工具之一：

- **参数对比**：多个参数的含义、默认值、影响范围用表格呈现，比段落文字清晰得多
- **方案对比**：设计决策的替代方案用对比表格
- **状态转换表**：简单状态机用表格比状态图更紧凑
- **错误码/错误类型**：错误信息、触发条件、处理方式用表格

### 认知负荷控制技巧

**分层披露**：先给概览，再给细节

```
概览层：一张流程图展示全局
  ↓
分析层：叙事讲解每个环节的设计决策和关键代码
  ↓
实现层：代码片段展示具体实现
```

**视觉锚点**：在长章节中定期用图表给读者"重新定位"

- 每个 h2 大节后建议有一张概览图
- 代码走查超过 3 个函数时，用流程图标注当前位置
- 状态变化多的模块，用状态图标注当前讨论的状态

**信息密度平衡**：

- 纯文字连续超过 8 段，应插入图表、表格或代码块调节节奏
- 连续 3 个代码块之间，应有叙事段落或图表连接
- 每个 h3 小节的内容量控制在读者 2-3 分钟可读完的范围内

## 内容深度标准

### 每章最小量

| 章节类型 | 中文字符（不含代码） | HTML 大小 |
|----------|-------------------|----------|
| 核心章节 | 3000-5000 | ≥ 20KB |
| 概览章节 | 1500-2500 | ≥ 10KB |
| 速查/索引 | 800-1500 | ≥ 6KB |

### 代码讲解深度

深度通过叙事自然达到，而非通过逐函数检查清单：

- **核心函数**：在执行路径中展示代码、讲解逻辑、分析设计，而不是单独罗列签名和参数
- **参数**：在代码执行到该参数时自然讲解，说明含义、典型值和修改影响
- **错误路径**：在执行到对应代码时讲解，说明触发条件、降级策略和下游影响
- **类**：在首次使用时讲解职责和核心方法，不单独成节罗列所有方法

### 设计决策讲解

每个重要的设计决策应包含：

- **选择**：项目选择了什么方案
- **原因**：为什么（从代码证据推断，或引用注释）
- **替代方案**：还有什么选择
- **权衡**：获得了什么、放弃了什么
- **修改影响**：如果改变这个决策会怎样

### 算法讲解

每个关键算法应包含：

- 核心思想和直觉
- 在本项目中的具体实现（标注代码位置）
- 关键参数如何影响结果
- 复杂度和性能特征
- 替代方案（如有）

## 知识扩展

### 核心原则：不打断叙事

知识扩展的首要约束是**不能破坏代码讲解的叙事连贯性**。

如果读者正在跟随一条执行路径理解代码，此时插入一个 sidebar 讲 A* 算法原理，读者的思路就被打断了。更好的做法是：

- **前置背景**：在开始讲解这段代码之前，先用 1-2 个自然段介绍必要的背景知识，然后顺畅地进入代码
- **融合讲解**：把知识扩展融入叙事段落中，而不是抽出来放进 sidebar
- **后置补充**：如果某个知识点不影响理解当前代码但值得一提，放在当前叙事段落结束后

### 何时使用 sidebar

只有当知识扩展**本身就是一个完整话题**、且不打断当前叙事流时才使用 sidebar：

- 章节之间的过渡区域（不在代码走查中间）
- 当前叙事已经完成一个完整主题后的补充
- 与当前代码无直接关系但读者需要知道的工程背景

### 扩展深度

由"理解当前代码所需的最小充分深度"决定：

- **行内解释**：一句话能说清的（如类型注解含义）
- **段落说明**：一段话能说清的（如框架某配置项的作用）
- **知识框**（sidebar）：需要 3-8 段说清的（如设计模式、算法原理）
- **背景小节**：需要更长篇幅的（写成当前路线中的背景段落）

### 知识框内容

sidebar 知识扩展应覆盖：

1. 解决什么问题（给读者建立动机）
2. 机制如何工作（不只是名词定义）
3. 当前代码哪几行依赖它（锚定到代码）
4. 为什么采用这种方式（设计权衡）

**知识扩展后必须回到项目代码**：在当前项目中哪个参数决定了什么行为，修改会影响什么。

### 知识扩展类型

| 类型 | 触发条件 | 重点 |
|------|---------|------|
| 语言特性 | 代码使用描述符、泛型、生命周期等 | 核心机制 + 本项目用法 + 常见陷阱 |
| 框架原理 | 代码依赖中间件、ORM、信号等 | 工作原理 + 项目配置 + 调试入口 |
| 设计模式 | 代码应用策略模式、观察者等 | 意图 + 项目实现 + 扩展方式 |
| 算法/数据结构 | 代码实现特定算法或选择影响性能 | 核心思想 + 参数影响 + 复杂度 |
| 工程实践 | 代码体现特定实践（日志、错误处理） | 做法 + 原因 + 新增代码时遵循什么 |

### 密度控制

- 每章 sidebar 不超过 3-4 个，且分散在不同小节
- **禁止在一段代码走查叙事中间插入 sidebar**
- 已在前文解释过的概念，后续只引用
- 重复机制只在首次出现时完整扩展

## 写作风格

### 代码讲解

- 直接陈述行为："这段代码做了 X"，不用"我们来看"
- 设计决策用分析语气：列出选择、原因、权衡
- 修改影响用务实语气："修改 X 会影响 Y，因为 Z"

### 知识扩展

- 先给直觉，再给精确描述，再回到项目代码
- 用简化独立示例解释机制，再映射回项目代码
- 不说"可自行查阅"——必要知识必须在指南内讲到位

### 排版

- 中英文间加空格
- 代码缩进 4 空格
- sidebar 标题不参与页面大纲
- `h3/h4` 表达真实层级，不用粗体段落冒充标题

## 知识扩展框（sidebar）

知识扩展/侧边栏用**标签化引用块**写（MD 作者约定见 `md-authoring.md`），builder 自动升级为 HTML `.sidebar` 组件：

```markdown
> **[理论说明]** A* 启发式权重
> 默认 1.0 保证最优；> 1.0 加速搜索但可能牺牲路径质量……
```

## 反模式（出现即重做）

| 反模式 | 诊断 |
|--------|------|
| 全章 < 1000 字 | HTML < 10KB |
| 代码片段无讲解 | 代码块后无自然段 |
| 只提函数名不贴代码 | 搜索不到 `<pre>` 块 |
| 知识扩展不回扣代码 | 扩展结束后无项目代码映射 |
| 同一机制多处重复展开 | 未使用交叉引用 |
| **函数签名罗列** | 每个函数单独成节，只有签名+参数列表+代码块，无叙事串联 |
| **叙事被 sidebar 打断** | 一段代码走查中间插入 sidebar，读者思路断裂 |
| **执行路径不连贯** | 读者无法从入口跟到出口，代码讲解在不同函数间跳跃 |
| **代码为主体而非叙事** | 页面是代码块的序列，文字只是代码的注释而非独立的讲解 |
