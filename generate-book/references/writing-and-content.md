# 代码库写作与内容指南

代码库模式的写作纪律：产出**项目精通指南**——读者能把每个关键行为追溯到源码位置、理解设计选择的理由。读 `shared/writing-core.md`；MD 约定读 `md-authoring.md`。任意技术栈通用。覆盖发现 → 分析 → 规划 → 写作。

## 发现（Phase 0）

识别源文件/测试/配置/资源；确定语言、框架、依赖、构建命令、入口点；**分类每个文件**——核心路径（深读）/ 支撑路径（概要）/ 参考（确认后排除）；识别端到端执行路径（输入 → 模块 → 输出）。输出 `{RUN}/codebase-map.md`（入口命令、主流程时序带 file:line、关键数据结构、失败路径）。**不按目录树逐个分析**。自检：每个相关文件已分类或附理由排除、无遗漏。

## 分析（Phase 1）

先建运行路线，再按优先级（入口 → 主流程 → 核心算法 → 状态/副作用 → 基础设施）分析模块。每核心模块写 `{RUN}/analysis/{module}.md`，聚焦：

- **接口与行为**：公共 API 签名/参数语义/返回值、核心控制流与数据流、错误路径与边界。
- **设计决策**：为什么选这个数据结构/算法/模式？替代方案？权衡？（无注释则标 V4 推断）
- **核心算法**：核心思想 + 复杂度 + 关键参数如何影响结果 + 本项目具体用法。
- **隐含知识**：理解这段代码所需的语言特性/框架机制/算法理论，标在何处讲透。
- **执行路径位置**：该模块在全局链路里的角色。

每断言标 `file:line` + 验证等级。源文件 >30 个时按模块分组（5-8 文件/组）分批。**防流水账**：提炼"为什么/怎么工作"，不是章节草稿，不逐行解释 import/常量。

## 规划（Phase 2）

定义目标读者与前置知识；章节按**内容逻辑**排序（非目录树）；每章：一个明确焦点 + 覆盖的源文件 + 知识扩展点 + 延后范围。原则：每个模式只详述一次其余交叉引用、核心执行路径无缺口。输出 `{RUN}/chapter-plan.md`。

## 写作原则

1. **叙事连贯**：代码讲解是讲故事不是列清单——沿执行路径/数据流/设计思路用连贯叙事串联，读者读完后能在脑中重建完整执行画面。
2. **先图后文**：复杂流程先用图给全局视觉框架，再叙事讲细节，再代码展示实现。认知负荷显著降低。
3. **设计优先**：先讲"为什么这样设计"，再讲"代码如何实现"。
4. **深度优先**：宁可少覆盖也要讲透——有代码、有分析、有背景、有权衡。
5. **不重复 / 就地讲透**：同一机制讲一次后续交叉引用；读者需要的背景在当前上下文讲到位，不要求外查。
6. **写人话 / 去 AI 腔**：用具体名词、确切动词，不堆空洞大词、不写模板化"安全"句（delve into / 值得注意的是 / 赋能…）。叙事驱动天然反 slop——跟着一条执行路径讲**具体的事**，就不会回归均值；写不出具体细节往往是没读透，回去补证据而不是用大词填空。

## 叙事驱动的代码讲解

首要任务不是"覆盖每个函数"，而是**让读者理解一条完整的思路**。

**好**（叙事驱动）：读者跟着一条请求从入口走到出口，代码片段在叙事需要时自然出现，参数和设计决策在上下文中解释。

> 当一条请求到达时，`Service.handle()` 先把输入归一化（`service.py:L34-38`）——后续所有处理都依赖归一化结果，原始格式无法直接用。归一化后调用 `Engine.run()` 启动核心循环（`engine.py:L67-98`），每次从队列取出下一项……关键设计是用优先队列而非 FIFO：代价是 O(log n) 入队，但保证关键任务先处理……

**坏**（碎片拼贴）：每个函数一段签名 + 一段代码 + 简短说明，中间被 sidebar 打断，读者看到的是孤立签名列表，看不到协作。

**代码是叙事的证据，不是主体**：先讲思路再贴代码；代码后紧跟分析（关键设计/参数影响/边界）；长代码（>80 行）只贴关键 20-30 行并标注源位置；**不在叙事中间插 sidebar**——背景知识是理解当前代码的前提就直接在叙事中讲。

按代码长度选展示：`<30 行`完整展示；`30-80 行`分段标注位置；`>80 行`只贴关键段。

**参数与错误路径**：不在签名处机械罗列，在代码执行到该参数/该错误分支时自然讲解（含义、典型值、修改影响；触发条件、降级、下游影响）。

## 可视化与认知负荷

用 ` ```mermaid ` 写图，下一行写图注（以"图"开头触发自动编号，证据 file:line 写图注里）。类型：`flowchart`（流程/架构）、`sequenceDiagram`（时序/调用链）、`stateDiagram-v2`（状态机）、`classDiagram`（类型关系）。

**必须用图的场景**：3+ 模块协作、状态转换、复杂执行路径（进代码走查前先给全局流程图）、数据变换链。**用表格的场景**：多参数对比、方案对比、错误码/错误类型、简单状态机。

**节奏**：纯文字连续超 8 段应插入图/表/代码调节；连续 3 个代码块间应有叙事或图连接；每章 sidebar ≤3-4 个且分散。

## 内容深度

**设计决策**（每个重要决策含）：选择 / 原因（从代码证据推断或引注释）/ 替代方案 / 权衡（获得什么放弃什么）/ 修改影响。
**核心算法**（每个关键算法含）：核心思想与直觉 / 本项目具体实现（标代码位置）/ 关键参数如何影响结果 / 复杂度与性能 / 替代方案。

## 知识扩展（sidebar 纪律，一处定义）

首要约束：**不打断叙事连贯**。读者正跟一条执行路径时插入 sidebar 讲算法原理 = 思路断裂。三档处理：
- **行内/段落**：一两句或一段能说清的（类型注解含义、某配置项作用）→ 直接在叙事中讲。
- **前置背景**：是理解当前代码前提的 → 讲解前先 1-2 自然段介绍再顺畅进入代码。
- **sidebar**：仅当扩展本身是完整话题、且当前叙事已完成一个主题（章节过渡区 / 主题收尾后），与当前代码无直接关系但读者需要知道。sidebar 须覆盖：解决什么问题（动机）→ 机制如何工作 → 当前代码哪几行依赖它 → 为什么这么做（权衡），**最后必须回到项目代码**（哪个参数决定什么行为、修改影响什么）。

## 反模式（出现即重做）

| 反模式 | 诊断 |
|---|---|
| 函数签名罗列 | 每函数单独成节，只有签名+参数+代码，无叙事串联 |
| 叙事被 sidebar 打断 | 一段代码走查中间插 sidebar |
| 执行路径不连贯 | 读者无法从入口跟到出口，讲解在函数间跳跃 |
| 代码为主体 | 页面是代码块序列，文字只是代码注释 |
| 代码片段无讲解 | 代码块后无自然段分析 |
| 知识扩展不回扣代码 | 扩展结束后无项目代码映射 |
| 同一机制多处展开 | 未用交叉引用 |
