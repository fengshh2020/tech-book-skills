# 代码库写作：沿执行路径把代码讲透

代码库模式的写作纪律：产出**项目精通指南**——读者能把每个关键行为追溯到源码位置、理解设计选择的理由。读 `../../shared/writing-core.md`（讲解质量三标准 / 反冗余 / 铁律）。

## 发现与分析

- **发现**：识别入口 / 测试 / 配置；语言、框架、构建命令；把文件分类——核心路径（深读）/ 支撑（概要）/ 排除（附理由）。识别端到端执行路径（输入 → 模块 → 输出）。**不按目录树逐文件分析**。
- **分析**：按优先级（入口 → 主流程 → 核心算法 → 状态与副作用 → 基础设施）读核心模块，记进 `{RUN}/progress.md`：公共 API 与语义、控制流 / 数据流、设计决策（为什么这样选、替代方案、权衡——无注释则标推断）、核心算法（思想 + 关键参数影响 + 复杂度）、该模块在全局链路的位置。每论断 `file:line`。

## 写作：叙事驱动 + 细致走读

**首要任务不是覆盖每个函数，是让读者理解一条完整的思路。**

1. **叙事驱动**：读者跟着一条请求 / 一次执行从入口走到出口，代码片段在叙事需要时出现，参数与设计决策在上下文中解释。

   > 当一条请求到达时，`Service.handle()` 先把输入归一化（`service.py:34-38`）——后续处理都依赖归一化结果，原始格式无法直接用。归一化后调用 `Engine.run()` 启动核心循环（`engine.py:67-98`），每次从队列取出下一项……关键设计是用优先队列而非 FIFO：代价是 O(log n) 入队，但保证关键任务先处理……

   反例（碎片拼贴）：每个函数一段签名 + 代码 + 简短说明——读者看到孤立列表，看不到协作。

2. **代码逐段走读**：贴出的每段代码紧跟讲解——这段做什么、关键行为什么这样写、改动会影响什么。`<30 行`完整贴；`30-80 行`分段标位置；`>80 行`只贴关键 20-30 行并标源位置。**没有走读的代码块不要贴**。
3. **参数与错误路径在执行到时讲**（含义、典型值、修改影响；触发条件、降级、下游影响），不在签名处机械罗列。
4. **可视化优先**（writing-core）：3+ 模块协作、状态转换、复杂执行路径、架构分层——先图后文（SVG，作者约定见 `../../shared/md-authoring.md`；证据 `file:line` 写图注）。多参数对比、错误码用表格。
5. **设计优先**：先讲"为什么这样设计"，再讲"代码如何实现"。每个重要设计决策含：选择 / 原因 / 替代方案 / 权衡 / 修改影响。
6. **背景就地讲**：理解当前代码所需的前置知识直接在叙事中带出（1-2 自然段），不打断叙事插讲义；sidebar 仅用于完整独立、且叙事已收尾的扩展话题，须回扣代码（每章 ≤3）。

## 反模式（出现即重做）

| 反模式 | 诊断 |
|---|---|
| 函数签名罗列 | 每函数单独成节，只有签名+参数+代码，无叙事串联 |
| 代码为主体 | 页面是代码块序列，文字只是代码注释 |
| 代码无走读 | 代码块后无"做什么/为什么/改动影响"的分析 |
| 执行路径不连贯 | 讲解在函数间跳跃，读者无法从入口跟到出口 |
| 同一机制多处展开 | 未讲透一次 + 交叉引用，而是换地方再讲一遍 |
| 叙事被 sidebar 打断 | 代码走查中间插入扩展话题 |
