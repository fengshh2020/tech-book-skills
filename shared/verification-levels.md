# 验证等级体系

> 供 review-tech-book 和 integrate-books 共享。定义事实性断言的验证等级和强制规则。

---

## 强制规则（在任何断言前必须检查）

- 🔴 严重错误 → 必须至少 V2（不能仅凭 V4 推断）
- 🟠 错误 → 必须至少 V2
- API 存在性/移除时间线 → 必须达到 V1 或 V3
- V4 推断 → 严重程度自动降一级，报告注明"未经验证"
- 整合产出新增代码 → 必须至少 V2 或 V1，不允许 V4
- 验证证据标注：`<!-- V1: 已通过 Python 3.14 验证 -->` 或 `<!-- V2: 来源 FP §2.3 -->`

## 等级定义

| 等级 | 含义 | 验证方式 | 报告标记 |
|------|------|----------|----------|
| **V1** | 实机验证 | 运行了代码、调用了 `hasattr()`/`dir()`、执行了 `python -c "..."` | `[V1 实机验证]` |
| **V2** | 源文件确认 | 实际读取了源文件对应行，确认引用内容存在 | `[V2 源文件确认]` |
| **V3** | 文档对照 | 查阅了官方文档/PEP/What's New 并引用了具体来源 | `[V3 文档对照]` |
| **V4** | 推断 | 基于一般知识推断，未实际验证 | `[V4 推断]` |

## 为什么等级顺序如此重要

实际项目中出现了多次误报：审阅者声称某 API 在特定版本被移除（V4 推断，且推断错误），如果强制标注等级，读者会知道这条未经实机验证，可以降低信任度。每条事实性断言的可信度应该对读者透明。将强制规则放在等级定义之前，是因为执行者在标注等级时应该先检查强制规则是否满足，再选择等级值。
